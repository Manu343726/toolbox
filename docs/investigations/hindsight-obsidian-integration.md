# Hindsight's Obsidian integration — a full survey

**Status: investigation. Nothing here is a decision.** This records what a
first-party Hindsight client does, in enough detail to be used or to be argued
with. The specification that consumes it is [`../knowledge.md`](../knowledge.md);
§7 of this document is the mapping, and the only part of this file that is an
opinion.

**Why this document exists.** Hindsight ships a client that syncs a
human-maintained markdown vault into a memory bank. That is the same job as the
documentation half of the knowledge subsystem, so either it removes that work or
it does not, and the difference is worth knowing precisely rather than in the
abstract.

**What was read, and when.** Every file of
[`hindsight-integrations/obsidian/`](https://github.com/vectorize-io/hindsight/tree/v0.10.1/hindsight-integrations/obsidian)
at tag `v0.10.1` except the npm lockfile — 42 files, of which 32 are source or
test, including all 13 spec files. Plus the published docs page, the changelog,
the npm registry metadata, and the API description (`openapi.json`, 0.10.1) for
every claim about the backend. Read 2026-09-27.

**What this document is not.** It is not a port plan. §7 says what would be
adopted; §8 says what would not, and §9 records four things that are worth
knowing and are not recommendations.

## 2. The features, from the outside

Stated as a person would meet them.

- **Incremental one-way sync.** Every note in the vault becomes a document.
  Edits replace, deletions remove, renames are a delete plus a create. A content
  hash means an unchanged note costs nothing.
- **Implicit scoping.** Each note is auto-tagged at ingest with its vault, every
  ancestor folder, and created/updated year and year-month buckets. A person
  chooses scope at recall time, not at write time. Several vaults share one bank
  and stay separable by a `vault:` tag.
- **A grounded chat panel.** `reflect` over the whole bank, with the notes it
  used listed and clickable, and a disclosure showing each reasoning step.
- **Manual or live.** A "Sync vault now" command, a "Ingest current note"
  command, sync-on-edit, and a CLI `--watch` mode.
- **Ownership, deliberately narrow.** Chat turns are **not** stored by default,
  and the setting says why: *"When on, chat turns are stored in Hindsight —
  this creates memory that does NOT live in your vault."*
- **Two frontends, one behaviour.** The CLI drives the same engine as the
  plugin, so a vault synced on a headless server and later opened on a laptop
  produces identical document ids, tags and prune ownership.

The one-way rule is the plugin's own hard rule, quoted from `README.md`:

> A hard rule of this plugin: **Hindsight is never a second source of truth.**
> Sync is **one-way**: Obsidian → Hindsight.

and it is a numbered design clause — `settings.ts` cites `DESIGN.md §0.5` for
`rememberConversations: false`, and `tests/chat.spec.ts` enforces it by name:
*"§0.5: does NOT retain conversation when rememberConversations is off"*.

> `DESIGN.md` is referenced from six places in `src/` and **is not in the
> repository** at `v0.10.1`. The clause numbers are therefore not checkable by a
> reader — only the code that cites them is. The three that carry the design are
> recoverable that way: **§0.5** is the one-way rule (`sync.ts`, `settings.ts`,
> `chat.ts`, `chat-view.ts`), **§4.1** is one shared bank separated by `vault:`
> tags rather than one bank per vault (`main.ts:152`), and **§4.6** is why scope
> is expressed as tags at ingest instead of folders at write time
> (`sync.ts:155`). Worth knowing before quoting any of them at anyone.

## 3. How it is put together

```
             ┌───────────────┐        ┌──────────────┐
             │ main.ts       │        │ node/cli.ts  │   frontends
             │ Obsidian API  │        │ argv, watch  │
             └───────┬───────┘        └──────┬───────┘
                     │ SyncVault / SyncFile │  ← the seam
             ┌───────▼───────────────────────▼───────┐
             │ sync.ts — SyncEngine                  │   the engine
             │ identity, digest, ownership, prune   │   pure logic
             └───────┬───────────────────────┬───────┘
                     │                       │
        ┌────────────▼──────────┐  ┌─────────▼───────────────┐
        │ obsidian-transport    │  │ fetch-transport         │  transports
        │ (Obsidian requestUrl) │  │ (global fetch)          │
        └────────────┬──────────┘  └─────────┬───────────────┘
                     └───────────┬───────────┘
                        ┌────────▼─────────┐
                        │ client.ts        │  one HTTP client, shared
                        │ 4 calls, no deps │  verbatim by both frontends
                        └────────┬─────────┘
                                 │  ┌──────────────┐
                        index ───┴─▶│ json-index.ts│  ownership record
                                 │  └──────────────┘  (CLI only)
```

Four decisions in that shape carry most of the weight.

**The engine is written against its own minimal interfaces.**
`SyncEngine` takes a `SyncVault` (`getMarkdownFiles`, `read`) and a `SyncFile`
(`path`, `stat.mtime`, `stat.ctime`) — "a subset of Obsidian's `Vault`/`TFile`
so it can be unit-tested without the Obsidian runtime". The plugin passes
`this.app.vault as unknown as SyncVault`. The CLI passes `FsVault`. **That
double cast is the load-bearing line in the codebase**: it is what makes a
second frontend possible at all, at the cost of a promise the compiler cannot
check.

**`client.ts` is shared verbatim, and the file says why:**

> This file has no runtime dependency on `obsidian`, so it is shared verbatim by
> both frontends and their request semantics can never drift apart.

**Enumeration and scope are different jobs.** `fs-vault.ts`: *"Note-level
include/exclude scoping is the engine's job (`SyncConfig.includeFolders`/
`excludeFolders`), not the vault's."* The vault answers "what markdown exists";
the engine answers "what is in scope".

**The clock and the writer are injected.** `new SyncEngine(..., index, persist,
nowIso)`. Every test passes `() => "T0"`. Nothing in the engine reads the wall
clock or writes a file itself.

## 4. The sync engine, mechanism by mechanism

### 4.1 Identity

`docId(path)` is the note's **vault-relative path**, prefixed with the vault name
when `prefixDocId` is on (the default). There is no frontmatter id.

```ts
docId(path: string): string {
  return this.config.prefixDocId ? `${this.config.vaultName}/${path}` : path;
}
```

The reason for prefixing is concrete, from `settings.ts`:

> On by default: all vaults share one bank, so document ids must be vault-prefixed
> to avoid cross-vault collisions (e.g. two vaults both having `Notes/todo.md`).

`FsVault` guarantees the path half is host-independent: *"paths are vault-relative
and POSIX-separated (so document ids/tags match the plugin's regardless of host
OS)"*. A `folder:` tag containing a backslash would be a different tag on Windows.

**Consequence: a move is a delete and a fresh extraction.** `handleRename`
deletes the old document and force-ingests the new path, and the integration test
is named `rename = delete old document + ingest new path`. Reorganising a vault
costs a full re-extraction of everything moved.

### 4.2 Change detection

Two stages, in this order, and the tests cover both:

1. **`mtime` equal to the recorded one → return `skipped` without reading the
   file.** The comment says why: *"Cheap pre-filter: same mtime as last sync →
   nothing to do (no read)."*
2. **`mtime` moved, `sha256` identical → refresh the recorded `mtime`, do not
   re-ingest.** *"mtime moved but content is identical — refresh the mtime,
   don't re-ingest."* Test: `hash-gate: skips re-ingest when mtime moved but
   content is identical`.

The digest is `sha256:<hex>` of the **raw file**, taken before frontmatter
stripping. An unchanged file is free; a touched file is free; a rewritten file
costs a read and nothing else until the decision to ingest.

### 4.3 Ownership, pruning, and the index binding

This is the part that was a shipped bug, and it is the most valuable thing in the
codebase.

**Prune by the local index, never by listing the base.** Verbatim:

> Prune by local index, NOT by listing server documents. Listing would also
> surface docs we don't own (e.g. opt-in conversation memory under
> `conversation/…`, or notes from another tool sharing the bank) and we'd
> wrongly delete them. The trade-off: orphans created while the local index was
> lost (reinstall) aren't auto-pruned — re-deleting the note fixes that.

Both halves of that are worth having: the failure being avoided, and the cost
being accepted **and named**, with the recovery ("re-deleting the note").

**The index is bound to its destination and fails closed.** `IndexIdentity` is
five fields:

```ts
{ apiOrigin, bankId, vaultPath, vaultName, prefixDocId }
```

and the module header states the harm the binding prevents:

> Reusing a vault-name-only index across banks/targets would silently classify
> the old target's files as "already synced" against the new one (leaving it
> incomplete) and could authorize prune DELETEs against a bank this ingester
> never wrote to.

`loadIndex` **throws `IndexIdentityError`** when the persisted identity differs,
and the message names every field that moved, with both values. The file name
carries a `sha256` fingerprint of the canonical identity (first 12 hex), so two
targets get different default files and the collision cannot happen by accident.

Three further properties, each with a test:

- **A legacy index is refused, not adopted.** An envelope with no `identity` —
  i.e. anything written before 0.2.1 — raises *"predates target binding and
  cannot be safely reused"* with instructions. Adopting it silently is exactly
  the bug being fixed.
- **Scope is deliberately not bound.** *"Include/exclude scope is deliberately
  not bound: on the same destination, narrowing scope legitimately prunes the
  newly-excluded docs (this ingester owns them there). The described cross-target
  harms all require a destination change, which is what this binding refuses."*
  Tested both ways: a bank/API/path/name/prefix change rejects; an
  include/exclude change reuses.
- **The API origin is canonicalised and carries no secret.**
  `https://user:pw@host:8888/v1/default?x=1` → `https://host:8888`. The index
  lives on disk, so it must not hold a credential.

**Durability and degradation.** Writes are `tmp` + `rename`, *"atomic replace —
never leave a half-written index"*, tested by asserting no `.tmp` survives. A
corrupt index is **not** fatal:

> A corrupt index means a full re-ingest (hash-skips unchanged) rather than a
> crash; warn because orphan pruning can't run until the index is rebuilt.

That is the whole degradation story in two sentences: what still works, and what
does not until repaired.

**Where it lives.** `~/.hindsight/obsidian/<vault>-<bank>-<fingerprint>.json`,
outside the vault, *"deliberately outside the vault so Obsidian Sync never
propagates it and it can't collide with the plugin's own index on another
machine"*. The plugin's equivalent is its own `data.json`.

### 4.4 Scope

`shouldInclude`: `.md` only (case-insensitive), then any `excludeFolders` prefix
match excludes, then — if any `includeFolders` are set — at least one must match.
Dot-directories are skipped at enumeration: `.obsidian`, `.trash`, `.git`, *"they
hold config and history, never vault notes"*.

Narrowing scope prunes. `excludes a folder and prunes notes that become
excluded` is a test, and it is the behaviour the unbound-scope decision in §4.3
exists to permit.

### 4.5 What goes on the wire

Four calls, all through `client.ts`.

**Ingest** — `POST /v1/default/banks/{bank}/memories`

```json
{ "items": [{ "content": "…", "document_id": "Work/a.md",
             "context": "obsidian", "update_mode": "replace",
             "tags": ["vault:V", "folder:Work", "created:2026", "alpha"],
             "metadata": {"folder": "Work", "vault": "V", "path": "Work/a.md"},
             "timestamp": "2026-03-15T00:00:00.000Z" }],
  "async": true }
```

**Delete** — `DELETE /v1/default/banks/{bank}/documents/{document_id:path}`,
where the path segment is encoded per component with the slashes preserved.

**Reason** — `POST /v1/default/banks/{bank}/reflect` with `{query, budget,
include: {facts: {}, tool_calls: {}}, tag_groups}`, preferring `tag_groups` over
`tags` because *"tag_groups and tags are mutually exclusive server-side"*.

**Health** — `GET /health`, for a settings-pane connectivity test.

**Tags generated at ingest**, from `path` and `stat`:

| Tag | Form | Example |
|---|---|---|
| vault | `vault:<name>` | `vault:Brain` |
| folder, one per ancestor | `folder:<cumulative path>` | `folder:Work`, `folder:Work/Clients` |
| created, two buckets | `created:<YYYY>`, `created:<YYYY-MM>` | `created:2026`, `created:2026-03` |
| updated, two buckets | `updated:<YYYY>`, `updated:<YYYY-MM>` | `updated:2026`, `updated:2026-06` |

plus the author's own frontmatter `tags` and `aliases`, deduped, order preserved.
Dates are bucketed because, as the code says, *"Recall has no hard date-range
filter, so date scoping is expressed as an OR over buckets."*

**Metadata generated at ingest:** every frontmatter scalar that is not a tag or a
date (quotes stripped), plus `folder` (omitted at the vault root), plus `vault`,
plus `path`. **`path` is the field that makes a hit clickable** — the plugin
strips the vault prefix off a returned `document_id` with `stripDocPrefix` to
resolve it to a file.

**`timestamp`:** frontmatter `created`, then `date`, first one wins; otherwise
`stat.ctime`.

**Concurrency:** ingest runs three at a time (`mapLimit(files, 3, …)`).

**An empty body is not ingested:** `if (!note.body) return "skipped"; // nothing
to ground on`.

### 4.6 Events, coalescing, and watch

**The plugin** puts create and modify into a `Set` of dirty paths and flushes on
a **4-second window** — `debounce(() => void this.flushDirty(), 4000, false)`,
with `resetTimer` false so the window does not slide on every keystroke. Repeated
edits to one file collapse to one path. **Delete and rename are not coalesced**;
they run immediately.

**The CLI** uses `chokidar` with `ignoreInitial: true`, any path segment starting
with `.` ignored, and `awaitWriteFinish: {stabilityThreshold: 300, pollInterval:
100}` to *"coalesce partial saves"* — the filesystem equivalent of the plugin's
window, and the right answer for an editor that writes in two steps. A rename
arrives as `unlink` + `add`, which the engine handles as delete-then-create: *"the
engine handles correctly as delete-then-create — same net result as the plugin's
dedicated rename path."* That sentence is the whole argument that the two
frontends can share a bank.

**Both frontends report the same six things** (`getSyncStatus`):
`{configured, syncing, pending, synced, lastSyncAt, error}`. The status bar
refreshes on a 30-second interval so "x ago" stays live, click re-syncs, and
`prioritises in-flight syncing over a prior error`.

## 5. The citation machinery, and the trap in it

This is the most consequential finding in the survey, because it is a place
where a reasonable-looking contract is wrong.

**`reflect`'s citations do not carry a document id.** From `reflect-util.ts`:

> reflect's `based_on.memories` do NOT carry document_ids, but the
> recall/expand tool outputs do (including nested `source_facts` for
> observations). So the authoritative "which notes were retrieved" list comes
> from walking the trace.

A cited fact is `{id, text, document_id?}`. Resolving a citation to a file
therefore requires **joining against `trace.tool_calls[].output`**, which does
carry `document_id`: index the trace into `fact id → document id`, then resolve
each cited fact through it. `groundedNotes` is that join, and it is careful about
what it is reporting — it returns only the notes the answer *cited*, deduped, in
citation order, and falls back to the whole retrieved set only when the answer
cited nothing resolvable. The comment is candid about the alternative: the
trace-derived set is *"the agent's whole scratchpad"*, a much looser list.

**So a citation costs a trace walk, and the trace is not free.** `include` on
`reflect` is *"disabled by default"*; the plugin turns on `facts` and
`tool_calls`, and `ReflectIncludeOptions` is exactly `{facts, tool_calls}`. For
recall, `IncludeOptions` is `{entities, chunks, source_facts}` with
`entities` defaulting to `{max_tokens: 500}`.

**Three separate notions of "what was used"** exist in one file —
`retrievedNotes`, `retrievedNotesDetailed`, `groundedNotes` — and the difference
is not refactoring, it is a product decision about what a person is shown.

## 6. What the tests establish

Thirteen spec files, 102 cases, and no Obsidian runtime anywhere in them:
`vitest.config.ts` aliases the `obsidian` package to a mock, with the reason
*"The real `obsidian` package has no runtime outside the app"* — which is the
`SyncVault` seam in §3 paying for itself. Two things in the tests are worth more
than the features.

**Parity is asserted, not assumed — twice, independently.**

1. `reconcile-integration.spec.ts`, *"dual-ingester parity"*: the filesystem
   frontend and a plugin-style in-memory frontend, same files, same config, same
   mtimes — the `retain` calls must be identical after normalising tag order.
2. `fetch-transport.spec.ts`, *"cross-transport request parity"*: the same
   `retain` built under two different transports must be the same request.

And the reason is written down where the seam is: `client.ts` is shared *"so
their request semantics can never drift apart"*. **Three expressions of one
discipline** — one implementation, one seam, and a test that the two sides agree.
This is the same rule a framework reaches for when two paths produce one artifact.

**Determinism is defended in the test, with the reason.** The parity test pins
`created:` in frontmatter and comments why:

> utimes can only set mtime, and birthtime behaves differently across OSes
> (macOS clamps it to a past mtime, Linux does not), which would otherwise make
> this compare platform-dependent.

`watchVault` is split out of `startWatch` *"so tests can drive real filesystem
events and then close the watcher, instead of blocking forever"*, with a
`WatchOverrides` parameter to *"tighten the debounce / force polling for
deterministic CI behavior"*. Real watcher, no sleeps, no hang.

**The edge cases, as a list** (abridged; the rest are in the files):

- unchanged note → no call at all; content changed → exactly one `retain`;
  `mtime`-only touch → nothing
- deleted note → `deleteDocument` with the exact id, **exactly once**
- rename → `deleted: 1` and `added: 1`
- excluding a folder prunes what it previously owned
- `prefixDocId` → `Brain/note.md`
- frontmatter `tags` flow through beside the generated scope tags; `created:`
  wins as the timestamp
- an empty body after frontmatter is not ingested
- unicode and spaces in filenames
- an **unterminated** frontmatter block is treated as plain body, not as an error
- `canonicalApiOrigin` strips path, query and credentials
- a corrupt index is empty plus one warning, not a crash
- each of the five bound fields rejects an index bound elsewhere; scope does not
- the refusal message names the field and both values
- `--index` reused across two banks is refused (issue #3257)
- `health()` returns false when the transport rejects
- no `Authorization` header when no token is set
- a non-2xx error carries the first 500 characters of the body
- `§0.5: does NOT retain conversation when rememberConversations is off`

## 7. What we take from it

The mapping, requirement by requirement. **This section is the opinion; the rest
of the document is not.** "Adopt" means the mechanism transfers as-is.

| Requirement | Verdict | What transfers |
|---|---|---|
| **W-6** digest-based diffing | **Adopt** | The two-stage filter: `mtime` skips the read, `sha256` decides. Strictly better than "digest, never timestamp" alone. |
| **W-7** ownership and pruning | **Adopt wholesale** | Prune by the ownership record and never by listing. Bind the record to `(api origin, base, corpus root, id namespace)`; refuse a mismatch naming every differing field; refuse a record with no binding rather than adopting it; keep the file name fingerprinted; write `tmp` + `rename`; treat a corrupt record as empty *and name the capability that is now unavailable*; deliberately do **not** bind scope. |
| **W-17** a base is rebuildable | **Adopt the mechanism** | A lost ownership record must be cheap, and it is cheap only because of the hash gate. That is the argument for W-6 being a requirement and not an optimisation. |
| **W-14** the corpus is the source of truth | **Adopt the enforcement** | The invariant lives in a named clause, the setting that would violate it defaults off *with the reason inline*, and a test enforces it by name. |
| **W-8** frontmatter to tags | **Adopt, extended** | Ancestor-folder tags, year/month date buckets, author tags passed through beside them. Plus the correction that `path` belongs in `metadata`, not in a tag — a citation needs a field to point at. Reserve `vault:`/`folder:`/`created:`/`updated:` in the provenance namespace. |
| **W-12** asynchronous, batched, idempotent | **Adapt** | `async: true` is a flag on the ingest request, and `items` is a list, so a batch really is one request. **But the client sends one item per request and no `operation_id`** — see §9. |
| **W-5** identity from the file | **Adapt, and say why we differ** | Namespacing identity for shared bases is right, and `two vaults both having Notes/todo.md` is the argument for it. The frontmatter `id` is kept, because a move is a delete and a full re-extraction here, and a corpus gets reorganised. |
| **W-4** reconcile is plan/apply | **Reject the absence** | There is no plan. `reconcile()` writes and returns a summary afterwards. The summary's four counts are a good shape; the confirmation is ours. |
| **W-10** no event time means timeless | **Adopt as an addition** | The client has no notion of timeless material: it always sends a `timestamp`, defaulting to `stat.ctime`. The API's `'unset'` goes unused. |
| **W-16** drift in the other direction | **No analogue** | Nothing in the client reports what the base believes that the corpus contradicts. |
| **W-18** commit correspondence | **No analogue** | No commit, no revision, no history. Not one field. |
| **W-19** reconcile on merged content | **Deliberate disagreement** | The client's `syncOnEdit` defaults **on** and `--watch` is a headline feature. See below. |
| **W-21** contradictions preserved | **No analogue** | Nothing resolves or reports a conflict. |
| **W-9** entity resolution off | **Adopt, and fix a bug** | See §9 — the client never sets `resolve_entities`, and the default is `true`. |
| **X-1…X-9** the whole-wiki view | **No analogue** | The client has no read path beyond its own chat. |
| **M-1…M-9** the mount | **No analogue** | Neither here nor in `hindsight fs mount`, which is a different program over a different endpoint. |

### 7.1 The four ideas that are not tied to a requirement

- **The status model.** `{configured, syncing, pending, synced, lastSyncAt,
  error}` is a better answer to "what is the state of this?" than a boolean. A
  reconcile plan should report the same six things.
- **Parity tests across every seam.** Two frontends over one engine got a parity
  test; two transports over one client got another. Wherever this design has two
  paths to one artifact — a subsystem and a `cmd/`, a provider and a test double
  — the test that they agree is the thing that keeps them honest.
- **Injected clock, injected writer.** Nothing in the engine reads the wall clock
  or touches the filesystem. That is why its tests need no sleeps.
- **Normalise paths to slashes at the boundary,** and treat a corpus's
  "created" date as approximate — `birthtime` is unreliable on Linux filesystems
  and reported as zero by some, which is why `FsVault` falls back to `ctime`.
  Prefer a declared date, and say which one was used.

### 7.2 The one real disagreement, and it is not a detail

**W-19 versus `syncOnEdit`.** The client syncs every few seconds while a person
types. This design refuses to believe unreviewed content and reconciles merged
commits instead.

Both are correct for their corpus. A personal vault has no review step and no
second reader, so waiting for a merge would mean never syncing; a shared corpus
is reviewed in Git precisely so that what the deployment believes was somebody's
decision. **This is why the client cannot simply be pointed at a repository**
(§8), and it is the one place where adopting its behaviour would change what the
system is rather than how it is built.

## 8. What we do not take

**It cannot be adopted as an implementation.** Four reasons, in order of weight:

1. It is TypeScript against the Obsidian runtime. A Go subsystem using it means
   shelling out to an npm CLI — a second, unmanaged writer to the base.
2. Its ownership record is bound to the corpus's **absolute path**, so a fresh
   clone anywhere else fails closed and forces a full re-extraction. For a Git
   repository, whose whole point is that it is cloned to many paths, that is
   disqualifying.
3. It records no commit, produces no plan, and confirms nothing (§7's table).
4. It has no notion of `authority`, `supersedes`, `status`, `owner` or `reviewed`
   — the frontmatter contract is most of what the documentation half is for.

**What a user can legitimately do today.** Point the CLI at a plain markdown
directory and get most of W-4 to W-8:

```sh
hindsight-obsidian-sync reconcile --vault ./docs --bank project --watch
```

That is worth documenting rather than rediscovering, and worth documenting with
its costs: no plan to confirm, no record of which commit was reconciled, no
authority metadata, and an index bound to the checkout path. It is a stopgap for
one person, not the subsystem.

## 9. Four things worth knowing that are not recommendations

**a) The client never sets `resolve_entities`, and the default is `true`.**
`MemoryItem.resolve_entities` is documented as: *"'True' (default) matches each
name to a similar existing entity when it scores above the match threshold, so a
name close to one already in the bank may resolve to that one instead of the one
you wrote. 'False' takes your names literally."* For an authored runbook, "Acme
Corp" in a new page can resolve to a different "Acme" already in the bank. This
is W-9, the default is the wrong side of it, and the shipped client is on the
wrong side. Anyone porting this must set it explicitly.

**b) `operation_id` exists and is unused.** On `RetainRequest`: *"Optional
client-supplied UUID used as the identity of an async retain operation.
Re-submitting with the same operation_id returns the original operation and
creates no new work, so retrying after a lost or timed-out acknowledgement will
not enqueue a duplicate. Reusing an id that belongs to a different operation
returns HTTP 409. Ignored for synchronous retain."* That is the mechanism for
idempotent batches, with a named conflict status. The client sends none, so a
retry after a timeout duplicates work.

**c) `observation_scopes` interacts with provenance tags, and nobody sets it.**
`per_tag` runs one consolidation pass per tag, `combined` (the default) runs one
pass with all tags together, and `shared` runs one pass over a single global
untagged scope, *"useful for deduplicating across volatile per-call provenance
tags"*. A corpus ingested with `vault:`, `folder:`, `created:` and `updated:`
tags is mostly provenance tags, and `per_tag` would fragment observations
accordingly. Choosing deliberately is better than inheriting `combined` without
knowing the question exists.

**d) Three state and documentation defects, one of which is in a shipped test
name.**

- `cli.spec.ts:259` is named *"refuses a stale --index whose scope changed,
  preventing cross-target deletes"* — but its body changes the **API origin**,
  with the inline comment saying so, and scope is deliberately *not* bound
  (§4.3). The name contradicts the test and the design; copying the name rather
  than the mechanism would bind scope and break the legitimate
  narrow-the-scope case.
- The published docs page still documents the pre-0.2.1 index path
  `~/.hindsight/obsidian/<vault>.json`, which is the shape that provokes the hard
  "predates target binding" error after upgrading — the error is correct and the
  page that triggers it is not.
- **`manifest.json` still says `version: 0.2.0` while `package.json` says
  `0.2.1` and npm is at `0.3.0`.** Obsidian reads the manifest for the plugin's
  own version, so the plugin reports a version two releases behind the code
  actually running. Anyone pinning on the reported version is pinning on a
  number the release process stopped updating.

Also, smaller: `types.ts` models four of the five `match` values (omitting
`exact`) and only `leaf`/`and` of the server's `and`/`or`/`not` tree, as a
deliberate subset — so a reader could mistake the client's subset for the
server's capability. And `reconcile-integration.spec.ts:180`'s comment claims the
index names a document that was never on disk, which the test does not set up;
the assertion `toHaveBeenCalledExactlyOnceWith` does prove the point, so the
coverage is fine and the comment overstates it.

## 10. What would change this survey

- A **backend** feature for authored content — a writable page body, a corpus
  endpoint — would change the specification's premise rather than this survey.
  §5 of
  [`hindsight-knowledge-backend.md`](hindsight-knowledge-backend.md) has the
  evidence that neither exists at 0.10.1, and the check is one grep.
- A **newer release** could set `resolve_entities`, adopt `operation_id`, or add
  a plan/confirm step. There have been six releases in sixteen weeks and the
  project is not conservative about changing its API — 0.3.0 added a
  consolidation knob with no changelog warning that it changes behaviour.
  Re-read the changelog before porting anything from §7.
- **Upstream answering**
  [discussion #4830](https://github.com/vectorize-io/hindsight/discussions/4830)
  — asked 2026-09-27, unanswered when this was written, and §5.6 of the backend
  survey records what each possible answer would change.
